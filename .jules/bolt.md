## 2026-09-02 - Memoization of static prompt section generators in system prompt builder
**Learning:** `build_tiered_prompt` was re-building static prompt text sections (`_build_identity_section`, `_build_boundaries_section`, `_build_safety_section`, `_build_format_rules_section`, `_build_mode_section`, `_build_channel_section`) on every chat request. These sections perform identical dictionary lookups, list operations, and string joins based on static JSON configurations. Decorating these pure section builders with `functools.lru_cache` eliminated redundant section assembly overhead, speeding up prompt construction from ~60.9us to ~45.7us per call (~1.33x faster / ~25% reduction in prompt assembly overhead).
**Action:** Use `functools.lru_cache` to memoize static section generators that read from immutable JSON templates and static system configurations in hot LLM prompt assembly pipelines.

## 2026-09-01 - Skip cross-locale regex evaluation in safety pattern matching
**Learning:** `_find_matches` and `_has_exclusion_context` in `SafetyService` iterated through all candidate rules and exclusion patterns regardless of the specified locale. When a specific locale was provided (e.g. `'en'` or `'ar'`), regex checks were unnecessarily executed against patterns designed exclusively for another language. Skipping rules and exclusions where `locale != "auto"` and `rule.source_locale != "auto"` and `rule.source_locale != locale` eliminated cross-locale regex matching overhead, speeding up message safety classification from ~134us to ~94.7us per call (~1.41x faster / ~30% reduction in regex scanning overhead).
**Action:** When matching rules or regex patterns against user input with a known language/locale context, skip executing rules explicitly targeted at other locales while preserving universal (`'auto'`) rules.

## 2026-08-31 - Redundant text sanitization in tag deduplication
**Learning:** `_unique_ordered` in `RAGService` called `sanitize_text(str(value), 120)` on every item being deduplicated. However, callers like `_clean_terms` passed items processed through `_clean_list`, which already performed regex sanitization (`sanitize_text`) and bounds checking (`safe_truncate`). Eliminating the redundant `sanitize_text` call inside `_unique_ordered` cut tag processing overhead from ~69.35us to ~32.87us per 100k operations (~2.11x faster).
**Action:** Avoid calling heavy regex-based text sanitization or normalization routines inside internal collection deduplicators when the input collections have already been sanitized upstream.

## 2026-08-28 - Frozen safety decision singleton and deferred match ref allocation
**Learning:** `classify_input` in `SafetyService` was constructing a new Pydantic `SafetyDecision` instance on every safe message pass (~99%+ of inputs), allocating empty lists for non-matching rules in `_match_rule`, and evaluating generator expressions in `_has_exclusion_context`. Setting `frozen=True` on `SafetyDecision` allowed reusing a module-level `_SAFE_DECISION` singleton safely, returning a shared `_EMPTY_MATCH_REFS` tuple deferred list allocations, and using explicit loops eliminated generator overhead, reducing 50,000 classification passes from ~12.55s to ~10.75s (~13.3% faster execution / ~33us per call saved).
**Action:** Mark Pydantic result models as `frozen=True` when returning default responses to safely reuse module-level singletons, and return empty immutable tuples from matching helpers to avoid list allocations on non-matching paths.

## 2025-05-20 - Pre-compiled module-level pattern tuples and explicit loops in classifier
**Learning:** `classify_message` was constructing temporary `list(_ALL_GREETINGS)` heap allocations and evaluating generator expressions inside `_contains_any` on every single incoming chat message classification pass. Pre-compiling JSON pattern lists into immutable module-level tuples at load time and using an explicit `for` loop in `_contains_any` reduced 250,000 classification iterations from ~8.27s to ~6.38s (~23% faster execution speed).
**Action:** When matching substring patterns in hot Python code paths, pre-compile keyword lists into module-level immutable tuples and replace generator expressions in `any()` with explicit `for` loops to eliminate frame and allocation overhead.

## 2025-05-19 - Fast tuple prefix checking and single-pass list cleaning in memory service
**Learning:** `_strip_instruction_prefixes` was allocating a new list of prefix strings and a generator expression on every single line of message text, while `_clean_memory_list` ran `_redact_memory_sensitive` and `sanitize_text` on every list item before passing it to `_unique_clean`, which ran the exact same 5 regexes and PII sanitization a second time. Using native C `str.startswith` with a module-level tuple of prefixes reduced line filtering from ~1.05s to ~0.22s (~4.7x faster), while delegating directly to `_unique_clean(..., max_chars=220)` reduced payload cleaning time from ~2.11s to ~1.41s (~33% faster).
**Action:** Use module-level tuples for `str.startswith()` prefix checks to leverage Python's native C tuple prefix matching, and avoid nested data-cleaning functions running redundant regex/redaction passes on the same items.

## 2025-05-18 - Precompute RAG unit search terms for linear-time retrieval
**Learning:** RAG unit retrieval scoring was re-tokenizing, lowercasing, sanitizing strings, and re-building candidate sets on every single query for all GroundingUnits in memory. Precomputing search terms (`PreparedSearchTerm` dataclass with tokens and lowercased string), category/technique lowercased strings, candidate sets, and normalization factors during `reload()` reduced 100 retrieval iterations from ~0.93s to ~0.08s (~11.6x faster retrieval / ~15x faster scoring).
**Action:** When working with static or loaded corpus structures in python memory, precompute search tokens, lowercased keys, candidate lookup sets, and normalization factors once at load time rather than inside query execution loops.
